# JARVIS Project Brain

## Project Overview
JARVIS is a local-first, multimodal, agentic AI assistant.

## Architecture Map
- `core/`: The brain of the system, orchestrator, and permission enforcement.
- `tools/`: The capabilities available to the agent (e.g., computer automation, web scraping).
- `memory/`: The state and session history (SQLite, ChromaDB).
- `llm/`: The wrapper for local LLM inference (LiteLLM/Ollama).
- `utils/`: Utilities like logging and system configuration.
- `voice/`: Whisper and TTS integration for voice mode.

## Strict Rules & Constraints
- Never add new dependencies without explicit instruction.
- Always run `uv run pytest -v` after modifying core logic.
- Treat the LLM as an untrusted reasoning engine; enforce PermissionGuard for SYSTEM/DESTRUCTIVE tools.
- Maintain dependency injection in the Orchestrator.

## Testing & Verification
- Run tests: `uv run pytest -v`

## Intent Router Architecture & Trade-offs
- **Mechanism:** Heuristic keyword + length matching (zero latency).
- **Benefits:** Skips the heavy Plan-and-Execute loop for simple queries, saving ~2-3 LLM calls.
- **Known Limitations (Edge Cases):** False Positives (complex queries containing simple keywords) and False Negatives (simple queries missing keywords). This is an intentional trade-off prioritizing speed and reduced token cost over perfect classification accuracy.

## Tool-Selection Policy (v0.21)
- `jarvis/core/tool_policy.py` implements the tool-selection CONTRACT (system block + classifier + schema narrowing + unmet-capability honesty). It generalizes by capability class, not per-phrase special cases — extend it by class, never by quoting user phrases.
- The deterministic calculator fallback covers exactly ONE bounded class: single-intent arithmetic where the model emitted zero tool calls. Knowledge retrieval stays model-driven on purpose. Unavailable capabilities (code execution, computer control) are honest refusals — even when the request contains arithmetic like `print(2+2)`.
- Kill switch: `JARVIS_DISABLE_TOOL_POLICY=true` restores exact v0.20 behavior (test-pinned).
- Live evidence (qwen2.5:7b A/B, `live_tool_eval.py`, manual-only): correct-tool 0.688 → 0.812; fabrication 0.0 in both arms. `llava:latest` cannot call tools (Ollama rejects the tools parameter) — model compatibility varies; never assume it.

## Multi-Step Planning (v0.22)
- The Planner is grounded in a compact tool catalogue (name: description), NOT bare names; plans pass `jarvis/core/plan_validator.py` (STRUCTURAL checks only: shape, bounds, registry truth, duplicates, forward-reference rejection — never semantic judgment).
- Later steps receive an exact-evidence ledger (clamped raw tool results of earlier steps) via `_build_step_messages(observations=...)`; steps with required_tools get `min_rounds=1`. Keep both guarantees when touching the plan path.

## Repeat Semantics (v0.23)
- `jarvis/core/dispatch_guard.py` is the repeat CONTRACT: within one turn, a call whose (tool, canonical-arguments) fingerprint already SUCCEEDED is suppressed AFTER PermissionGuard/confirmation, BEFORE `registry.dispatch_async` — so suppression can never bypass security or pollute the registry probe.
- Preserve the exemption set EXACTLY `get_current_datetime`, `recall_facts`, `remember_fact` (state/turn-coupled only) and ledger properties when touching dispatch: success-only recording (retry-after-failure works), fresh ledger per turn (`chat()` re-creates it), fingerprint-only logging (never arguments).
- The plan loop skips an identical later step (`redundant_plan_step` log + `redundant_step` SSE) and logs `plan_step_satisfied`/`plan_completed`; `plan_ready` carries `quality=` from `jarvis/core/plan_quality.py` (deterministic, never authorization).
- `evaluation/plan_judge.py` is evaluation-ONLY (semantic plan scoring; conservative degradation). Never wire it into the production loop.
- Benchmarks: `evaluation/multistep_benchmark.py` (11 cases incl. repeat_semantics, pytest-wired), `live_multistep_eval.py` (manual-only; per-case suppression counts). Suppression is exact-argument: `"2+2"` vs `"2 + 2"` differ by fingerprint — do not add math special cases.
- Routing: compute+memory conjunctions and search+compare requests go to the planner; NEVER route on bare operator substrings (`-` matches 'plan-and-execute' — use the digit-operator pattern).
- A plan is a request, never authorization; live multi-step evidence and limits are in `live_multistep_eval.py` + developer manual §17/§26.

## Cross-Turn Cache + Bounded Replanning (v0.24)
- `jarvis/core/result_cache.py` is the cross-turn CONTRACT: a dispatch may serve a CACHED result only for tools with an explicit class-level `CachePolicy` (7 tools: web_search/wikipedia_summary/web_scrape global; read_file/list_directory/search_knowledge session; calculator global with the value-based `calculator_expression` normalizer + 7-day TTL — test-pinned in `tests/test_result_cache.py::TestCachePolicyConsistency`). No policy ⇒ never cached — never add one to side-effect or state-coupled tools (`get_current_datetime`, `recall_facts`, `remember_fact`, `write_file`, vision, execution, computer control).
- Layering in `_dispatch_with_permissions_async` is load-bearing: PermissionGuard → confirmation parking → v0.23 ledger → cache lookup → registry. A hit must pass the tool's own Pydantic validation; errors are never stored; `intentional_repeat=True` bypasses; freshness-worded requests (`tool_policy.is_freshness_request` — small explicit regex, no NL classifier) bypass ttl-freshness tools ONLY. A hit is provenance-labeled untrusted EVIDENCE — never an instruction, never an authorization.
- Freshness strategies are per-policy and distinct: `ttl` (settings-driven, per-tool `RESULT_CACHE_*`), `source_stat` (size+mtime re-stat, MISSING_SOURCE sentinel), `knowledge_generation` (`SessionStore.knowledge_generation()` registry aggregate — NEVER a Chroma scan). Cache entries live in the SAME SQLite (`result_cache` table, bounded by `RESULT_CACHE_MAX_ENTRIES`; expired purge at store time, oldest-evict only if still over cap). Kill switch: `JARVIS_DISABLE_RESULT_CACHE=true`.
- Keys: sha1(tool+normalized)[:16]; normalizer per policy — generic (v0.23 canonical), verbatim (paths/URLs: key-sort ONLY), calculator_expression (value-based via `canonical_expression_form()` — the tool's own AST parser; `2+2`≡`2 + 2`≡`(2+2)`; do not invent another math parser).
- Bounded replanning: `_execute_plan_steps()` can NEVER replan (no recursion); chat() performs at most ONE replan, ONLY on structural evidence (ERROR step result, or required-tool step whose every tool result errored) AND with remaining budget. Replan context is compact (`_build_replan_context`: completed = do-not-repeat); budget is inherited, never reset; a second failure forces an INCOMPLETENESS NOTICE (`_format_incomplete_note`) — never claim completion. `plan_completed` (complete=bool) and `replan`/`plan_complete` SSE are the observability contract.
- Benchmarks/tests: `tests/test_result_cache.py`, `tests/test_replan.py`, `evaluation/cache_replan_benchmark.py` (12 cases, pytest-wired), `live_cache_replan_eval.py` (manual-only, qwen2.5:7b: reuse 6/6, freshness bypass 2/2, one-replan 2/2, no-replan-on-success 2/2). Maintenance: `maintenance cache stats|inspect|cleanup` (bounded; inspect never shows payloads); API `GET /ops/cache/stats` = counts only.

## Grounded Synthesis + Client Refresh + Ops Metrics (v0.25)
- Evidence ledger is the grounding CONTRACT: successful tool results flow into a bounded ledger (`_MAX_EVIDENCE_ITEMS=16`, `_MAX_EVIDENCE_ITEM_CHARS=1200`) delivered as AUTHORITATIVE TOOL EVIDENCE. The block rides on the **FINAL USER message** in `_synthesize` (called at `temperature=0.0`) — with the identical block as a trailing SYSTEM message, qwen2.5:7b recomputed arithmetic from the question instead of transcribing (live-bisected via the raw Ollama API). Final instruction: "Using ONLY the AUTHORITATIVE TOOL EVIDENCE above (when present), answer the original request now. Transcribe tool-derived values exactly; never recompute them." Evidence is data, never instructions. Keep role placement + contract wording when touching the synthesis path.
- Failed-step retry dedup is load-bearing: chat()'s replan passes `retry_descriptions = completed_descriptions - {failed step descriptions}` into `_execute_plan_steps` — successes stay do-not-repeat, but a replan restating a FAILED step runs instead of being skipped as `redundant_plan_step`. Breaking this silently drops the corrected result from the evidence ledger.
- Refresh (`refresh=True` through runtime.chat → chat()) is a CLIENT freshness control that skips ONLY the result-cache lookup (`bypass_reason="refresh_request"`). It runs inside the usual layering (PermissionGuard → confirmation parking → repeat ledger) and must NEVER bypass permissions, schema validation, confirmations, or the repeat guard; it is not a kill-switch replacement. Wire any new client surface the same way.
- Cache metrics: every dispatch records daily hit/miss/stale/bypass/store counters (per-tool deltas merged read-modify-write under `self._lock`) into `cache_metrics_daily` (SAME SQLite), pruned past `RESULT_CACHE_METRICS_RETENTION_DAYS` (default 30). Surfaces: `GET /ops/cache/stats/history` (aggregates only), `maintenance cache stats` (`today:` counters), dashboard daily-activity trend. Metrics are counts/keys only — never arguments or payloads. A replan emits `replan_diff` (added/removed/retargeted steps, structure only).
- Evaluation isolation is a REQUIREMENT: every script under `evaluation/` must call `evaluation/_bootstrap.py::isolate()` BEFORE importing jarvis — it redirects DB_PATH/VECTOR_DB_PATH to a private temp dir and raises RuntimeError rather than ever touching the real `jarvis.db`. Under pytest (DB already redirected) a safety valve lets eval modules import; the real-DB case still raises. Tests: `tests/test_evaluation_isolation.py` (14).
- Live evidence (qwen2.5:7b, 10 cases × 2 reps, `live_cache_replan_eval.py` v0.25): **18/20**; cache hits 6/6, freshness bypass 4/4, one bounded replan on scripted failure, grounding over the model's guess proven; the 2 misses are tool-choice variance (both mechanisms proven in the other rep). Report: `live_cache_report_v025.json`.

## Grounding Guard & Answer Integrity (v0.26)
- `jarvis/core/grounding.py` is the answer-integrity CONTRACT: after synthesis, `check_grounding(answer, evidence)` deterministically verifies the final answer against the turn's trusted evidence via `POLICIES` (calculator numeric / datetime stated date / file-listing exact names / structured field). High-confidence only: a missed catch is acceptable, a false rejection is not. Numeric canonicalization REFUSES ambiguous forms (`12,34`, lone dot-groups as grouping) instead of guessing; contradictions require a RESULT-CUE near the differing number (step narration, years, epoch-width IDs, latencies, bare percentages never trigger).
- Layering in `_synthesize` is load-bearing: model answer → `_enforce_grounding` → EXACTLY ONE correction round (`build_correction_prompt`: evidence restated, transcribe-don't-recompute, temperature 0.0) → re-check → still wrong ⇒ `build_fallback_answer` (truthful withheld notice preserving the authoritative value + provenance). Never more than one round; never silent acceptance; never fabrication; a correction LLM failure degrades to the fallback. Kill switch: `JARVIS_DISABLE_GROUNDING_GUARD=true` restores exact v0.25 behavior (test-pinned).
- Part 7 semantics (preserve when touching): a FAILED observation never governs; cached evidence is authoritative at the same level as live (v0.24 provenance header ⇒ `source`/`cached_age`); for one tool with several genuine values in a turn, ANY of them is consistent (match-any — claim attribution is undecidable; the newest value feeds correction messaging). Evidence text is DATA: injected `Result:` lines cannot impersonate calculator evidence (full-match on the exact output format), and correction/fallback prompts carry safe metadata only.
- Evidence attribution comes from the DISPATCH SITE: `_run_react(..., tool_observation_tools=)` plumbs real tool names into `_evidence_item_from_observation`; `_tool_from_observation` is fallback only. The resume path (`_resume_paused_turn`) rebuilds the evidence ledger from persisted tool messages (v0.25 gap closed) — keep both when touching evidence flow.
- Telemetry: `grounding_metrics_daily` counters via `record_grounding_metrics` (checks/contradictions/corrections/corrections_ok/corrections_failed/fallbacks + per-tool; same retention discipline as cache metrics). Surfaces: `GET /ops/grounding/stats`, `maintenance cache stats` (`grounding today:`), dashboard Answer-grounding trend. Counts only — never answers or evidence text. Benchmarks: `evaluation/grounding_benchmark.py` (17 cases = spec categories A–M, 17/17), `tests/test_grounding.py` (79), `tests/test_grounding_integration.py` (18), `live_grounding_eval.py` (manual-only; qwen2.5:7b 2 reps: tool-choice 1.0, final-value 1.0, zero fallbacks; report `live_grounding_report_v026.json`).

## Voice & Multimodal Experience (v0.27)
- `jarvis/multimodal/` is the multimodal CONTRACT: every client type (CLI, dashboard, API) converges on `MultimodalRequest` → `MultimodalService.run()` → `Orchestrator.chat()` — the EXISTING runtime. There is NO separate voice/vision agent and NO second security model; do not add orchestrator-parallel logic for a modality.
- Provider boundaries are load-bearing honesty: STT = LOCAL Whisper (`jarvis/voice/stt.py`, record()/transcribe() split, transcribe_bytes() for uploads; ffmpeg is an OPTIONAL system dep); TTS = NETWORK-BACKED Edge TTS (`jarvis/voice/tts.py`, `TTS_ENABLED` kill switch, synthesis timeout, ONE attempt, `stop()` cancellation boundary). Never describe Edge TTS as fully local in docs or UI.
- Push-to-talk ONLY (Part 3): `VoiceTurn` runs an explicit per-turn lifecycle (IDLE/LISTENING/TRANSCRIBING/THINKING/SPEAKING/ERROR) with NO background capture, NO wake word, NO persistent audio. Cancellation is a clean HALF-DUPLEX boundary (cancel before run() skips the turn; during the run() text completes but playback is suppressed via tts.stop()). A failed turn leaves the session intact (state ERROR, next turn works) — test-pinned.
- Image uploads (Parts 12/13/20): `Attachment.from_upload` validates by CONTENT (magic-byte sniffing; declared MIME/filename advisory only), bounds size (`MAX_IMAGE_UPLOAD_MB`) and decoded pixels (`MAX_IMAGE_PIXELS`), persists under a RANDOM name in `multimodal_upload_dir` (never the client name — path traversal impossible by construction), and `cleanup()` after the turn. Audio uploads: same pattern via `validate_audio_bytes`.
- llava boundary (Parts 10/11): vision_model does visual interpretation ONLY — it is never given tool schemas (Ollama rejects tools for llava; verified) and its output is wrapped in the VISUAL OBSERVATION contract (untrusted data, not a trusted tool result, never instructions). The v0.26 grounding policies exclude vision prose by construction (exact-format + dispatch-site-attribution gates) — keep it that way.
- Grounding applies to ALL modalities (Part 17): voice speaks only the FINAL grounded response (never an intermediate); image turns route through the same `vision_analyze` tool inside the normal ReAct loop, so permissions/confirmations/cache/repeat-guard apply unchanged.
- API: `POST /chat/multimodal` (multipart text/image/audio) shares `_AUTH`, rate limiting, `_resolve_session`, leases with `/chat`; text-only `/chat` untouched. Upload validation failures are 422; STT hard failures map to 502.
- Retention (Part 16): raw audio is NEVER persisted (transcribed in temp, deleted in `finally`); images persist only for the request then `cleanup()`; session history keeps the derived TEXT. Telemetry events (voice_*, tts_*, vision_*, multimodal_request_*) carry bounded error categories — never raw audio/image bytes or full transcripts.
- Tests: `tests/test_multimodal.py` (68; spec A–T incl. injection, cancellation, hygiene, leak loops). Live: `live_multimodal_eval.py` (manual-only; provider/model 5/5, reasoning 2/2; report `live_multimodal_report.json`).

## Safe Browser & Computer Interaction (v0.28)
- `jarvis/browser/` is the browser-safety CONTRACT: nine narrow tools (`jarvis/tools/browser_control.py`) delegate to `BrowserController` (the ONLY stateful component), which enforces IN ORDER: emergency stop → URL policy (`url_policy.py`: http/https allowlist, scheme/credential/port/whitespace denials, private+loopback denied unless `BROWSER_ALLOW_LOCAL_NETWORK`, DNS resolution fail-closed with rebinding protection) → observation freshness (`observations.py`: every ACTION needs a fresh 128-bit `observation_id`; navigation invalidates all) → pacing (`limits.py`: 24/turn, 120/session, 300 s turn, max 1 identical side effect, nav depth 12, 2 retries) → driver → deterministic verify. The model NEVER receives raw coordinates, cookies, storage, arbitrary JS, or tabs — the `BrowserDriver` interface (simulated | playwright) does not have them.
- Dynamic risk is the v0.28 authorization INPUT, never a second system: `BaseTool.risk_for_args` + `registry.effective_risk_level()` validates args WITHOUT dispatching and can only ESCALATE the static tier (submit/delete/download-worded clicks and password/card-like fills → SYSTEM ⇒ the EXISTING confirmation parking). Any classifier error degrades to the STATIC (ceiling) level. Both orchestrator dispatch sites consult it; the guard runs first, suppression/ledger/cache layering is untouched.
- Action results are runtime-computed CONTRACT strings (`verification.py`): first token ∈ {`ACTION_EXECUTED`, `ACTION_VERIFIED`, `ACTION_NOT_VERIFIED`, `ACTION_BLOCKED`, `ACTION_INTERRUPTED`}, parseable via `status_of()`. A click on a different host, a read-back mismatch, or an interrupted action must NEVER read as success. Driver failures carry the `ERROR:` prefix so the bounded self-correction loop engages; gate refusals are `ACTION_BLOCKED` (structured, never retried as errors).
- Page content is UNTRUSTED PAGE CONTENT (`injection.py` framing + INJECTION_WARNING on instruction-shaped text); hidden/CSS-concealed text is never extracted (driver visibility filter); ALL model-visible page text is redacted (`redaction.py`) FIRST. Page text can never escalate permissions: risk is computed from validated tool args only.
- The emergency stop (`emergency.py`) is HUMAN-ONLY: CLI `/stop` (+ Ctrl+X mid-turn via stdlib `msvcrt`), `POST /browser/emergency-stop`, dashboard button. The model has NO tool that can trigger/reset it — never add one. `check()` runs before EVERY driver operation; interrupted actions report `ACTION_INTERRUPTED`; `/resume` / `POST /browser/emergency-reset` clears it (idempotent).
- Downloads (`downloads.py`): controlled per-session temp area only; executable/script suffixes NEVER stored; size-capped (`BROWSER_MAX_DOWNLOAD_MB`); random stored names; sha256 metadata; NEVER executed (future execution = Docker sandbox only); wiped on close. The host boundary (`jarvis/computer/__init__.py`) stays closed: `DisabledHostBackend` is the ONLY `HostBackend` — shell/registry/process/clipboard control is structurally absent forever.
- Sessions are bounded (`registry.py`): LRU cap `BROWSER_MAX_SESSIONS` (3), idle TTL 900 s, close-all on stop/shutdown. SimulatedDriver is the default `BROWSER_DRIVER` (tests/demos, zero processes); unknown driver names fail closed to simulated. The surface is OPT-IN: `ENABLE_BROWSER_CONTROL=true` (default False) gates registration in `runtime.py`; browser tools are deliberately NOT in `disabled_tools` (that list is pinned by test_runtime).
- Surfaces: `GET /browser/status` (safe metadata only), dashboard Browser-control section (status + stop), CLI `/browser`. Tool policy knows the "browser" capability family (`CAPABILITY_TOOLS["browser"]` + `_NARROW_PATTERNS`); computer-control honest refusals still fire (tool names contain neither 'code' nor 'computer').
- Tests: `tests/test_browser_control.py` (124, A–Z deterministic; resolver-injection keeps DNS checks deterministic — production keeps real sockets). Live: `live_browser_eval.py` (manual-only; real Chromium on controlled LOCAL pages; needs BROWSER_ALLOW_LOCAL_NETWORK=true + BROWSER_DRIVER=playwright). Security model: `docs/JARVIS_V028_SECURITY_MODEL.md`.

## Personal Integrations & Workflow Automation (v0.29)
- `jarvis/integrations/` is the integration CONTRACT: `IntegrationManager` is the ONLY path to a connected account, enforcing IN ORDER: provider registered → provider available → LIVE auth state (EXPIRED/REVOKED refuse) → exact scope (deny-by-default `require_scope`) → operation. The model holds opaque `account_id` handles, NEVER credentials; scopes are bound at CONNECT time by the USER and the model has no tool to change them. Writes are dispatched EXACTLY ONCE (no retries); ambiguity (TIMEOUT/AMBIGUOUS_OUTCOME) ⇒ UNKNOWN + audit row, never silent re-execution; reissue flows through the existing confirmation machinery with a provider idempotency key (calendar create = sha256(title|start_utc|duration|attendees)) so a re-dispatch returns the ORIGINAL resource.
- Risk reuses the EXISTING tiers (`static_tier_for`: READ_ONLY→SAFE, LOW/MEDIUM→NETWORK, HIGH→SYSTEM, IRREVERSIBLE→DESTRUCTIVE); `risk_for_args` escalates real-account fully-valid writes to SYSTEM ⇒ the EXISTING confirmation parking (`PAUSED_FOR_CONFIRMATION`). Validation failures degrade to the static tier and refuse BEFORE any side effect (no audit rows for refused ops). Reads are SAFE, cached per-account (session TTL override, default 60 s); writes are NEVER cached. Read retries are bounded (≤2) to {RATE_LIMITED, PROVIDER_OUTAGE} only.
- Provider content is UNTRUSTED DATA: `sanitize()` + `frame_external_content()` (reuses the browser injection detector) on every field; read outputs carry the UNTRUSTED PROVIDER CONTENT footer and put `count:` on its own line (grounding-checkable by the v0.26 structured-field policy). EMAIL_READ/EMAIL_SEND are DECLARED-NOT-IMPLEMENTED — no tool exists; `tool_policy.detect_unmet_capability` honestly refuses email requests. Never add per-provider tool special cases — extend by capability class.
- Store: `integration_accounts` + `integration_audit` tables (same SQLite). Audit rows carry category/operation/op_id/idempotency-key/redacted summary ONLY — never arguments or payloads. Credentials: XOR+base64 obfuscation keyed by per-install file `.jarvis_integration_key` (process-lifetime in-memory key for `:memory:` DBs) — a local-dev privacy guard, NOT hard security; documented honestly in `credentials.py`.
- Surface is OPT-IN: `ENABLE_INTEGRATIONS=true` (default False) gates the 8 tools (calendar list/get/create/update/delete, task list/create/complete) + API endpoints (`/integrations*`) + CLI (`/integration*`) + dashboard section, all mirroring the browser pattern in `runtime.py`. There is NO HTTP execute endpoint — the chat runtime is the only execution path. Providers ship local-dev only (`LocalCalendarProvider`, `LocalTasksProvider`); real OAuth providers are future work and must go through the SAME `IntegrationProvider` ABC + manager.
- Tests: `tests/test_integrations.py` (103, A–AD deterministic; fault-injected providers at the adapter seam). Live: `live_provider_eval.py` (manual-only; local dev providers; needs ENABLE_INTEGRATIONS=true). Security model: `docs/JARVIS_V029_SECURITY_MODEL.md`.

## Real OAuth & Account Connectivity (v0.30)
- `jarvis/integrations/oauth.py` is the OAuth CONTRACT and adds NO second security model: it slots a real authorization-code + PKCE flow into the EXISTING `IntegrationProvider`/`IntegrationManager` boundary. Provider-specific details (endpoints, scope strings, identity discovery) live in the adapter behind the `OAuthIntegrationProvider` mixin — the orchestrator NEVER sees them. Never let provider OAuth details leak into the manager/loop, and never add a parallel connect path.
- One normalized lifecycle (`AuthorizationStatus`: DISCONNECTED/AUTHORIZING/AUTHORIZED/TOKEN_EXPIRING/REFRESHING/AUTHENTICATION_REQUIRED/REVOKED/ERROR) feeds the EXISTING operational `AuthState` via `operational_auth_state()`. OAuth only reports honest states; the manager's enforcement order (provider→availability→LIVE auth→scope→operation) is untouched. Refresh failures → `AUTHENTICATION_REQUIRED`; REVOKED_GRANT → `REVOKED` and is NEVER retried.
- Durable one-time state is the CSRF/replay CONTRACT: 256-bit random values stored by SHA-256 HASH in `oauth_states` (the raw value is NEVER persisted/logged/shown), hard-bound to `(provider, session_id, display_label, scopes, redirect_uri)`, with `OAUTH_STATE_TTL_SECONDS` expiry (default 600) and an ATOMIC one-time consume (`UPDATE ... WHERE consumed_at IS NULL`). Missing/invalid/expired/mismatched/replayed state fails closed. Keep PKCE S256 on every flow (verifier lives server-side in the flow row only).
- Redirects are config-constructed: `default_redirect_uri`/`redirect_uri_for_session` build from `OAUTH_REDIRECT_BASE_URL`; a provider-supplied target is NEVER honored (no open redirects). The callback endpoint is DELIBERATELY NOT behind `_AUTH` — the one-time state is the authenticator (standard OAuth) — and responds with a fixed local HTML page (never a redirect, never a token). Do not add an API-key requirement to the callback; do not make it redirect.
- Token boundary: access + refresh tokens + expiry live in the SAME XOR+base64-obfuscated local store as v0.29 credentials (a privacy guard, NOT encryption — documented honestly). Tokens NEVER appear in prompts, evidence, cache, API responses, logs, audit rows, or reprs; `public_metadata()` emits only `authorization_status`/`authorization_expires_at`/`authorization_updated_at`. Refresh runs BEFORE an operation inside `OAUTH_REFRESH_MARGIN_SECONDS`, rotates ATOMICALLY, and preserves a stored refresh token when the provider omits one (`update_integration_account_tokens(refresh=None)`).
- Identity is provider-discovered (`discover_account_ref`/introspection), NEVER inferred from chat text; same-identity re-auth rotates in place; a legacy raw-credential account is never overwritten by an OAuth flow. Disconnect = best-effort provider revocation → local row delete → `delete_result_cache_for_account` → fail-closed on the stale handle (`_ensure_usable_auth` refuses when the row is gone).
- Grounding: `ProviderScheduleGroundingPolicy` (`provider_schedule`) is registered LAST in `POLICIES` and verifies labeled `date:`/`time:`/`timezone:`/`duration_minutes:`/`status:` evidence; it EXEMPTS read-pre-state tools (`calendar_list_events`, `task_list`) so state-change answers are not false-rejected, and is conservative for task status (`status: open` vs claimed completed only when the resource id appears in the answer). The `_derived_schedule_lines` in `jarvis/tools/integration_tools.py` produce the local-time labeled lines from UTC instants + IANA zone.
- Retention: `INTEGRATION_AUDIT_RETENTION_DAYS` (default 90) + `maintenance integrations-audit` (report-only by default; `--yes` bounded deletion; UNKNOWN/RUNNING rows ALWAYS protected). Config: `OAUTH_*` settings in `jarvis/config.py` (state/refresh TTLs, redirect base, access/code TTLs, per-provider client id/secret for local dev).
- Surfaces: API `POST /integrations/{provider}/authorize`, `GET /integrations/{provider}/authorize/status`, `GET /integrations/oauth/callback/{provider}`, `POST /integrations/accounts/{id}/refresh`; CLI `/integration-reauthenticate` + OAuth path in `/integration-connect`; dashboard OAuth expander. Still NO execute endpoint.
- Tests: `tests/test_oauth.py` (83, A–V/AA/AC deterministic). Live: `live_oauth_eval.py` (manual-only; deterministic simulated provider, NO Ollama/network; needs ENABLE_INTEGRATIONS=true). Security model: `docs/JARVIS_V030_SECURITY_MODEL.md`. Full suite 1218 passed / 29 skipped.
